# 网站全栈工程师面试题与知识点

本文根据目标岗位的要求与职责整理，覆盖 Next.js / React、TypeScript、Node.js API、响应式开发、国际化、SEO、性能、部署运维、数据分析和交接协作。建议结合自己真实负责过的项目，用「背景—目标—方案—结果—复盘」组织回答；不要只背概念，尽量准备可量化的数据和故障案例。

## 一、项目经历与岗位匹配

### 1. 请介绍一个你独立负责并上线的网站

**考察点：** 项目 ownership、技术判断、交付能力、结果意识。

**回答要点：**
- 业务目标、用户和页面规模；自己负责的前后端与运维边界。
- 为什么选 Next.js、渲染策略、数据来源、部署架构。
- 如何拆分组件、接入 API、处理国际化、SEO、分析埋点。
- 上线流程、监控和回滚方案；上线后的性能、转化或收录结果。
- 遇到的最大问题、定位过程、复盘后做了什么改进。

### 2. 如何从零接手一个陌生的线上站点？

**知识点：** 先建立系统地图，再做低风险变更。

- 盘点仓库、依赖版本、运行时、环境变量、域名/DNS/SSL/CDN、服务器和部署流水线。
- 找出关键页面、路由、数据/API、第三方脚本、表单与线索流转链路。
- 查看监控、错误日志、Search Console、GA4/GTM、备份和回滚流程。
- 记录权限、账号归属、构建发布步骤、已知风险；先验证本地构建和回滚，再改动生产。

### 3. 运营或广告团队临时提出页面改版，如何评估和交付？

**回答要点：** 澄清目标、受众、语言、设计稿、截止时间、埋点/转化定义；评估复用组件、内容和接口依赖；按优先级拆分任务并标注验收标准；检查响应式、性能、SEO、埋点与表单；预览环境验收后分阶段发布，关注转化和错误指标。

## 二、Next.js 与 React

### 4. Next.js 的 SSR、SSG、ISR、CSR 分别适合什么场景？如何选择？

- **SSG：** 构建时生成，适合变化较少的公开内容页，缓存友好。
- **SSR：** 请求时生成，适合必须反映请求或用户上下文的数据。
- **ISR/按需再验证：** 静态产物按时间或事件更新，适合可接受短暂陈旧的内容。
- **CSR：** 浏览器加载后交互或请求，适合非 SEO 核心的强交互区域。
- 从个性化程度、更新频率、SEO、延迟、缓存成本和数据新鲜度综合判断；不必全站只用一种模式。

### 5. App Router 中 Server Component 与 Client Component 有何区别？

- Server Component 在服务端执行，可直接访问服务端数据/资源，减少发送到浏览器的 JS；不能使用 state、effect、浏览器 API。
- Client Component 通过 `'use client'` 建立客户端边界，负责状态、事件和浏览器交互；其依赖会进入客户端 bundle。
- 页面尽量维持服务端组件，交互区域再下沉为客户端组件；边界 props 需可序列化，避免整页无必要地客户端化。

### 6. 如何在 Next.js 中处理数据获取、缓存和重新验证？

- 明确数据是否公开、是否按用户隔离、允许陈旧多久；私有数据不能被跨用户共享缓存。
- 根据框架版本配置 `fetch` 缓存/再验证，或使用 `revalidatePath`、`revalidateTag` 等失效机制；理解请求级、数据级和路由级缓存的区别。
- 写操作后按数据依赖失效相关缓存；检查生产构建和部署环境的实际行为，避免依赖旧版本默认值。

### 7. React 中 state、props、受控组件和 effect 分别解决什么问题？

- props 是父级输入，state 是组件自身随交互变化的数据；避免冗余 state 和重复存储可推导值。
- 受控表单以 React state 为准，便于校验和联动；非受控适合简单表单或通过 ref 读取。
- `useEffect` 用于与外部系统同步（订阅、定时器、浏览器 API），不应把纯计算或事件逻辑都塞进 effect；清理副作用，处理竞态与重复请求。

### 8. 如何避免 React 页面不必要的重渲染？

先用 Profiler/性能工具确认瓶颈；再检查 state 放置、组件边界、列表 key、昂贵计算和对象/函数引用。按需使用 `memo`、`useMemo`、`useCallback`，避免盲目记忆化带来复杂度；大列表考虑虚拟化，首屏外内容延迟加载。

### 9. Next.js 动态路由、布局和错误处理如何设计？

说明 `app/` 路由段、动态参数、嵌套 layout、loading/error/not-found 边界的用途；错误边界应提供可恢复的用户体验并记录服务端错误。鉴权不能只靠隐藏 UI，需在服务端数据/API 层校验身份与权限。

## 三、TypeScript、JavaScript 与工程质量

### 10. `type` 与 `interface` 如何选择？如何为 API 响应建模？

- 两者都能描述对象结构；interface 可声明合并和扩展，type 更适合联合、交叉、条件/映射类型等组合。
- 用判别联合描述不同状态，如 `{ status: 'success'; data: T } | { status: 'error'; message: string }`。
- TypeScript 类型在运行时会被擦除；外部输入仍要用 Zod 等 schema 或手写校验进行运行时验证。

### 11. `any`、`unknown`、泛型和类型收窄分别是什么？

- `any` 关闭检查，`unknown` 要先验证再使用，优先 `unknown` 接收不可信数据。
- 泛型表达可复用函数/容器与输入输出之间的类型关系。
- 类型收窄通过 `typeof`、`in`、判别字段、自定义类型守卫等确认具体分支。
- 避免滥用类型断言掩盖接口不一致；边界数据要做运行时校验。

### 12. 解释闭包、事件循环、Promise 与 `async/await`。

- 闭包让函数保留创建时的词法环境；注意生命周期、循环引用和 React 闭包捕获旧值的问题。
- JS 执行包含同步调用栈、微任务队列与任务队列；Promise 回调通常在微任务阶段执行。
- `async/await` 是 Promise 的语法形式；并行独立任务用 `Promise.all`，要考虑失败处理、超时、取消和部分成功需求。

### 13. 如何保证代码规范和可维护性？

类型检查、ESLint/格式化、模块边界、命名和错误处理约定；复杂逻辑拆成可测试单元；PR 小而聚焦，说明原因、风险和验证步骤；代码评审关注正确性、安全、可读性、性能与回滚影响。

## 四、Node.js、API 与表单/线索链路

### 14. 设计一个网站询盘表单 API，需要考虑什么？

- 定义字段、格式、必填项、错误结构、幂等/重复提交规则和成功状态。
- 服务端校验不可省略；做长度限制、规范化、垃圾/机器人防护、速率限制和 CSRF/CORS 等适用防护。
- 使用 HTTPS；敏感信息不写入普通日志；配置超时、重试边界、请求 ID 和可观测性。
- 数据库/CRM/邮件等下游失败要有明确处理（队列、重试、补偿或告警），避免用户看到成功但线索丢失。

### 15. 浏览器表单提交成功，但 CRM 没收到线索，怎么排查？

沿链路逐段确认：浏览器网络请求与响应、服务端日志/请求 ID、字段映射和校验、CRM 认证/限流/响应、异步队列及重试、最终落库。检查是否误把下游失败吞掉；补充失败告警、死信/人工补发、去重和对账机制。

### 16. API 如何处理认证、授权、输入验证和错误？

- 认证确认调用者身份，授权确认其可执行操作；每个敏感资源都做服务端权限校验。
- 对 path/query/body 做 schema 校验、长度限制和输出编码；采用最小权限和安全的密钥管理。
- 返回稳定且不泄露内部细节的错误码/消息；日志保留上下文但脱敏，不回传堆栈或凭据。

### 17. Node.js 服务遇到高延迟或内存持续上涨，如何诊断？

先看请求量、延迟分位数、错误率、CPU、内存与事件循环延迟；结合 APM/日志/heap snapshot 定位慢 SQL、阻塞计算、未释放监听器/定时器、缓存无限增长或大对象引用。设置超时、并发/队列上限和资源限制，修复后对比指标。

## 五、HTML、CSS 与响应式实现

### 18. 如何把设计稿高保真还原并兼顾桌面和移动端？

先确认设计断点、内容优先级、字体与素材；用语义化 HTML、Flex/Grid、相对单位和合理断点；避免固定宽度导致溢出。图片按尺寸/格式响应式加载；用真实设备宽度检查导航、表格、表单、触控区域、折行和横向滚动。

### 19. 如何定位 CSS 布局问题？Flex 与 Grid 如何选？

使用浏览器开发者工具检查盒模型、计算样式、层叠来源和断点；Flex 适合单轴排列，Grid 适合二维网格；明确容器尺寸、`min-width: 0`、溢出和定位上下文。避免无边界的 `z-index`、全局选择器和高特异性覆盖。

### 20. 图片、字体和第三方脚本如何兼顾视觉与加载？

图片压缩并提供适当尺寸与现代格式，首屏关键图避免懒加载，非首屏延迟加载；字体限制字重/字符集并考虑预加载；第三方脚本评估必要性、异步加载及其对主线程和隐私同意的影响。

## 六、国际化与多语言 SEO

### 21. Next.js 多语言站点如何组织路由和翻译？

- 选择稳定的语言路由策略（如 `/en/`、`/fr/`），语言代码使用标准 locale；避免仅通过 IP 推断并强制跳转。
- 翻译资源按命名空间/页面拆分，插值、复数、日期、数字、货币使用国际化库；缺失翻译有明确 fallback。
- 内容、标题、描述、导航和表单提示都要本地化；注意 RTL、字体、长度变化、日期和货币格式。

### 22. `hreflang` 应如何配置？常见错误有哪些？

- 每种语言/地区版本互相列出 alternate，包含自身引用，并指向可索引的绝对 URL。
- 语言/地区代码合法且页面内容确实对应；避免所有页面都指向首页、错误 canonical、缺少互反标签或指向重定向/404。
- 为默认语言按需要配置 `x-default`；同时维护正确的 canonical、站点地图和内链。

## 七、性能、SEO 与爬虫可访问性

### 23. 什么是 LCP、CLS、INP？如何优化？

- **LCP：** 最大内容元素的呈现时间；关注 TTFB、首屏关键资源、图片尺寸/优先级、字体和阻塞脚本。
- **CLS：** 布局偏移；为图片/广告预留尺寸，避免无空间插入内容，谨慎处理字体切换和动态组件。
- **INP：** 交互响应体验；缩短长任务、减少主线程工作、控制客户端 JS 和第三方脚本。
- 区分实验室数据与真实用户数据，按页面模板和设备定位；发布后持续观察，而非只看单次 Lighthouse 分数。

### 24. 如何让搜索引擎发现、抓取并正确索引页面？

可抓取的服务端 HTML、可访问的内部链接、正确状态码、唯一且准确的 title/description/canonical；提供 sitemap 并在 robots.txt 中管理抓取；排查 noindex、重定向链、软 404、重复内容、孤儿页和 JS 渲染问题。robots.txt 控制抓取，不等于从索引中移除页面。

### 25. 结构化数据有什么作用？怎么验证？

使用符合页面实际内容的 Schema.org JSON-LD（例如 Organization、Product、Article、Breadcrumb）；字段必须准确且可见内容一致，不承诺一定展示富结果。避免虚构评分/信息；发布后用搜索引擎提供的结构化数据工具和 Search Console 检查错误与增强报告。

### 26. SEO 排名或收录突然下降，如何排查？

先确定影响范围、发生时间和业务影响；检查发布记录、HTTP 状态、robots/noindex/canonical、重定向、站点地图、模板内容、服务器错误和渲染结果；结合 Search Console 索引/抓取报告与查询/页面趋势定位。评估是否算法、需求或季节变化；先恢复技术故障，再验证抓取和排名恢复。

## 八、Linux、Nginx、Docker、CI/CD 与 Cloudflare

### 27. 描述一次从提交代码到生产上线的流程。

提交/PR → lint、类型检查、构建与必要检查 → 预览环境验收 → 构建不可变产物/镜像 → 部署 → 健康检查与冒烟验证 → 观察错误率、延迟和转化 → 必要时回滚。配置与密钥通过环境/密钥管理注入，不写进仓库；数据库变更需兼容新旧版本。

### 28. Nginx 反向代理通常负责什么？如何排查 502/504？

反向代理可终止 TLS、路由到上游、设置头部、压缩和缓存等。502 常见于上游不可用/连接失败，504 常见于上游超时；检查 Nginx error/access log、进程/容器状态、监听端口、DNS、网络、防火墙、上游超时和应用日志。不要仅通过无限增大 timeout 掩盖根因。

### 29. Docker 镜像如何做到安全且易部署？

使用精简基础镜像、多阶段构建、锁定依赖、非 root 用户、健康检查和合理信号处理；不要把密钥打进镜像；设置资源限制、日志策略并扫描依赖/镜像。区分镜像构建配置与运行时配置，生产只部署已验证的不可变镜像。

### 30. 如何设计可靠的回滚和备份？

保留可追溯的发布版本和配置；回滚前确认数据库迁移兼容性；定义备份频率、保留周期、异地副本和恢复目标，定期实际演练恢复；记录操作人、时间和结果。仅有备份文件但未验证恢复不能算可靠备份。

### 31. Cloudflare/CDN 缓存配置需要注意什么？

识别静态资源与动态/个性化响应；设置合理 Cache-Control、缓存键和失效策略；避免缓存含用户数据的页面/API；部署后验证边缘命中、源站请求、证书/DNS 和真实响应头。缓存问题可通过特定 URL/标签失效解决，谨慎全站清缓存。

### 32. 线上重大故障如何响应？

先确认影响和范围，按预案止损（回滚、降级、切流）；建立单一事实记录和负责人，检查日志/指标/最近变更；恢复后验证关键用户路径与数据完整性。事后记录时间线、根因、检测缺口和可执行改进项，避免只归咎个人。

## 九、GA4、GTM、Search Console 与转化分析

### 33. 如何设计从广告点击到询盘成功的测量链路？

定义业务转化及成功口径 → 设计事件名和参数 → 捕获必要的来源/活动信息 → GTM/代码触发 → GA4 调试验证 → 设为关键事件并与业务/CRM 对账。避免重复触发、PII 采集和只验证“事件发出”却不验证数据落地。

### 34. GA4 与 GTM 各自负责什么？如何排查事件没上报？

GA4 收集和分析事件数据；GTM 管理标签、触发器和变量的发布。逐段看 dataLayer 推送、触发条件、同意状态、容器版本、网络请求、GA4 DebugView/实时报告和过滤设置；检查重复标签、错误 Measurement ID 和环境差异。

### 35. Search Console 与 GA4 的数据有什么区别？

Search Console 关注 Google 搜索展现、点击、查询、索引和抓取；GA4 关注站内访问与事件行为。两者口径、时间、归因和采样/处理方式不同，不能期待数字完全一致；结合页面/查询和落地页表现判断问题。

### 36. 如何分析广告落地页转化下降？

按时间、渠道、活动、设备、国家、落地页分层；确认埋点和流量质量没有变化，再看页面速度、错误率、表单开始/提交/成功漏斗、表单后端成功率和线索质量。检查广告承诺与页面信息匹配、语言/移动端体验、加载和第三方服务；用对照实验验证改动效果。

## 十、Git、评审与协作

### 37. 你如何管理 Git 分支、冲突和代码评审？

使用短生命周期分支、清晰提交和 PR 描述；同步主干、理解冲突语义后人工解决；评审提供具体可操作意见，作者说明测试和风险；合并前确认 CI、审批和部署策略。敏感文件和生成产物遵循仓库约定，不提交密钥。

### 38. 如何与运营、广告、SEO 团队协作？

把需求转成可验收的用户路径、内容、语言、埋点和上线条件；澄清素材/文案/翻译责任人；用预览链接和检查清单验收；上线后共享指标和问题记录。对不可行或有风险的要求，解释影响并给出可落地选项。

### 39. 交接代码仓库、部署流程和账号权限时，必须留下什么？

仓库与分支策略、架构/依赖版本、开发构建命令、环境变量名称（不写秘密值）、部署/回滚步骤、域名/DNS/证书/CDN 配置位置、监控告警、备份恢复、第三方服务负责人、权限申请/回收方式、已知风险和故障联系人。凭据使用公司密码库或密钥管理系统交接并遵循最小权限。

## 十一、情景题与优先级

### 40. 页面上线后首屏变慢、广告转化下降，但没有明显报错，先做什么？

确认数据变化是否真实（监测配置、流量构成、设备/地区）；对比发布时间和版本；看真实用户性能、网络瀑布、第三方脚本、LCP 资源及表单漏斗；按影响面优先回滚高风险变更或关闭非必要脚本。快速止损后复现并量化根因，避免同时改多处而无法归因。

### 41. 发现机器人大量提交表单，如何兼顾转化与防护？

在服务端加速率限制、输入校验、蜜罐/风险评分或适度验证码；检查来源与提交模式，避免仅依赖前端隐藏字段；对可疑流量隔离并防止 CRM 被灌入。评估误伤真实用户，监控有效线索率和表单完成率，逐步调整规则。

### 42. 需求、SEO 与上线时间冲突时如何取舍？

先确认业务目标、必须项和风险；将功能拆成可独立发布的阶段，保证核心转化、可抓取性、跟踪和回滚；必要时缩减非关键装饰或延后低优先级内容。明确取舍、负责人和验证指标，不能用无监控、无回滚的方式赶上线。

- 准备一次性能优化、一次 SEO/索引排错、一次线上故障/回滚、一次 API/表单链路排障案例。

- 所有数据与案例以真实经历为准；若没有直接经验，说明理解、验证方法和迁移计划，不虚构生产经验。
